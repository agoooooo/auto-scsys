# 技术方案概要

## 1. 方案目标

实现一个 Android Python 自动化产品的 MVP，打通以下流程：

1. 用户登录并绑定一台或多台 Android 手机。
2. 用户上传 Python 脚本，查看版本和运行记录。
3. 用户在手机上获取脚本，阅读脚本来源及所需能力说明，确认后运行。
4. 脚本调用 Android App 提供的自动化能力，执行一个明确的场景，例如 OCR 识别屏幕文字并反馈结果。
5. 用户可从 Web 后台向自己的在线设备发起远程运行请求；Android 客户端通过服务端校验后自动启动并显示运行状态，不再逐次要求任务确认。
6. 管理员可以管理用户和设备、发布脚本版本并查看运行状态。

本方案允许用户上传并运行自定义脚本。脚本运行在 App 的权限边界内，可使用 App 已获得且用户已授权的能力；这不代表绕过 Android 系统权限或访问其他 App 的私有数据。

## 2. 技术栈建议

| 模块 | 建议技术 | 用途 |
|---|---|---|
| Android App | Kotlin、Jetpack Compose | 原生界面、账号设备管理、权限授权和任务状态 |
| Python 运行时 | Chaquopy | 将受支持版本的 Python 运行时集成到 Android App |
| Android 自动化能力 | Kotlin 原生 API + App 内部 Python 桥接接口 | 提供屏幕捕获结果、OCR、明确授权的交互能力给 Python 脚本 |
| 管理后台 | React、TypeScript、Vite | 管理用户、设备、脚本版本和运行记录 |
| 服务端 API | Python、FastAPI | 认证、授权、脚本版本管理、设备状态和运行记录 |
| 主数据库 | PostgreSQL | 用户、设备、脚本元数据、权限关系和运行记录 |
| 脚本文件存储 | S3 兼容对象存储 | 保存版本化脚本包；数据库只保存元数据及存储键 |
| 部署 | Docker | 部署 API 和后台；MVP 可使用托管 PostgreSQL 与对象存储 |

MVP 暂不引入消息队列、Kubernetes 和微服务。Android 客户端可通过定时轮询获取更新；确有实时通知需求后再评估推送服务。

## 3. 总体结构

```text
Android App
  ├─ Kotlin / Jetpack Compose：界面、账号、设备、权限说明、运行管理
  ├─ Python Runtime：加载并运行已下载的用户脚本
  └─ Native Bridge：提供经用户授权的 OCR、屏幕和交互能力
          │ HTTPS
          ▼
服务端 API（FastAPI）
  ├─ 认证与授权
  ├─ 用户、设备和脚本版本管理
  ├─ 脚本包下载及完整性校验
  └─ 运行状态和审计记录
       ├─ PostgreSQL：业务数据
       └─ 对象存储：脚本版本包
          ▲
          │ HTTPS
管理后台（React / TypeScript）
```

脚本在 Android 设备本地运行，服务端负责身份、授权、脚本分发、远程运行请求和记录，不在服务端代替手机执行自动化操作。

## 4. Android 执行设计

### 4.1 Python 与原生能力的分工

- Kotlin 负责 Android 生命周期、登录态、权限流程、前台任务状态和设备 API。
- Python 负责脚本逻辑、流程编排和对 App 提供能力的调用。
- 通过定义稳定、版本化的桥接接口，脚本只能调用 App 明确提供的能力；具体能力仍受 Android 系统授权控制。
- MVP 优先实现一个场景和少量接口，例如读取用户授权的屏幕内容、OCR 识别、返回结构化结果。后续再按需求增加交互能力。

### 4.2 脚本包与运行状态

- 每个脚本版本作为不可变版本保存，包含入口文件、依赖清单、脚本元数据和版本说明。
- 服务器提供的文件使用 TLS 传输，并在客户端按清单校验哈希；发布方签名可用于确认包来源和防止传输后被替换。
- 哈希和签名只能证明完整性或来源，不能证明脚本行为安全。
- 客户端保留最近可用版本；新版本下载或校验失败时不替换已安装版本。
- 运行状态至少包括：等待确认、准备中、运行中、成功、失败、已停止。
- 前台执行时展示可见状态和停止入口。需要持续运行时使用 Android 前台服务并遵循系统通知要求，不承诺被系统强行终止后仍可无感运行。
- 远程请求需绑定脚本版本、目标设备、发起人、有效期和唯一请求 ID，并经过服务端授权校验及审计记录。

### 4.3 本地确认与系统权限

- 用户在手机上主动选择本地脚本运行时，展示脚本名称、来源、版本、能力说明和风险提示，并要求明确确认。远程请求不要求逐次任务审阅或确认，由客户端在服务端校验通过后自动运行。
- 系统权限由 Android 正常授权流程取得；App 不尝试绕过权限、无障碍或屏幕捕获限制。
- 脚本只有在 App 已获授权的范围内才能调用相应能力。Android 的应用沙箱、权限模型和其他 App 数据隔离仍然有效。
- 用户可以停止运行、撤销系统授权或停用设备。

**权限边界：**Python 代码若在 App 进程中运行，通常能够使用该 App 进程可访问的能力和数据。Chaquopy 不是针对恶意脚本的安全沙箱；不能把任务确认或包签名描述为隔离或安全保证。远程自动运行具有较高风险；服务端仍必须校验账号、设备、脚本授权、版本和请求有效期，任务执行保持可见并提供停止入口。

管理员将脚本推送给其他用户或设备时，必须与用户本人上传运行分开处理：服务端明确限制发布者、接收用户/设备、脚本版本和能力范围。授权范围内的远程请求无需设备端任务确认；自动运行仍使用可见前台服务并提供停止入口。

### 4.4 后台远程运行

- 用户在 Web 后台选择自己的在线设备和已授权脚本，发起一次远程运行请求；服务端只下发请求，不在服务端执行手机自动化。
- 所有远程请求在服务端账号、设备、脚本授权、请求有效期及设备空闲检查通过后，由 Android 客户端自动批准并运行；无需逐次任务审阅、确认或设置预授权。任务通过可见前台服务运行，用户可随时停止。
- 设备通过定时轮询获取请求；离线或过期请求不执行，并在后台显示明确状态。后续如需实时性，再评估推送通知；推送不绕过 Android 的后台启动限制。
- 请求要求的无障碍服务必须已由用户在 Android 设置中启用。远程 OCR/屏幕捕获在有效的持续 OCR 前台服务会话中复用该会话，否则须打开 App 并完成 Android MediaProjection 系统授权；系统授权不是任务确认，拒绝系统授权则不执行。会话结束或系统回收后必须重新授权，客户端不尝试静默恢复。后台无法发起系统授权时通知用户打开 App，授权完成后继续处理。
- 任务运行时使用 Android 允许的前台执行方式，显示持续通知、运行状态和停止入口；不支持无运行提示或不可停止的静默执行。
- 若 Android 系统不允许后台启动，应等待用户打开 App 或确认，不能尝试绕过系统限制。

## 5. 主要业务流程

### 用户上传并运行

1. 用户登录后台或 App，创建脚本并上传版本包。
2. 服务端验证文件大小、格式、入口和版本元数据，保存版本并计算内容哈希。
3. 用户在手机端选择该脚本，客户端下载并校验版本包。
4. 客户端展示来源、版本、能力说明和系统授权状态。
5. 用户在手机端直接运行，或从后台向已绑定设备发起远程运行请求。
6. 设备在服务端鉴权通过后自动批准并运行远程请求，不进行逐任务审阅或确认。无障碍服务必须已由用户启用；远程 OCR/屏幕捕获须由设备用户完成 Android 系统授权。设备用户可主动开启持续 OCR 会话，在该会话有效期间复用屏幕捕获；会话结束后需再次系统授权。
7. App 在系统允许且用户可见的执行方式下启动 Python 脚本，通过原生桥接执行已授权的能力。
8. App 展示运行结果和错误摘要，并提交必要的运行记录。

### 管理员发布

1. 管理员创建或停用用户，查看其绑定设备。
2. 管理员选择脚本版本及目标用户或设备进行发布。
3. 服务端记录目标设备、脚本版本、发布者和接收状态；设备同步时只看到待确认发布的元数据及已确认版本。
4. 客户端展示发布来源、更新说明和能力范围；设备用户确认接收后，服务端才允许该设备下载对应脚本。
5. 管理后台查看版本分配和运行结果。

脚本发布本身不会自动触发执行。远程运行是独立操作：用户从 Web 发起请求后，设备端在服务端校验通过后自动运行并记录结果；请求均设置有效期。远程 OCR/屏幕捕获任务仍须由设备用户同意 Android 系统屏幕捕获授权；在用户主动开启的可见持续会话有效期内，可复用这次系统授权，不能静默获取或跨会话恢复权限。

## 6. 服务端与数据模型

MVP 核心实体建议包括：

- **User：**账号、邮箱、状态、设备数量上限。
- **Device：**所属用户、设备标识、型号、App 版本、最近活跃时间、状态。
- **Script：**脚本名称、所有者、描述及可见范围。
- **ScriptVersion：**版本号、对象存储键、内容哈希、入口、依赖清单、能力说明、创建者和发布时间。
- **ScriptGrant：**脚本版本对用户或设备的授权关系及状态。
- **TaskPublication：**管理员向指定设备分发的脚本版本、发布者、接收状态及确认时间。
- **RunAuthorization：**旧客户端兼容数据；当前 Android 客户端不使用逐任务运行预授权。
- **RemoteRunRequest：**远程运行请求及其发起人、目标设备、状态、有效期和关联运行记录。
- **RunRecord：**用户、设备、脚本版本、开始/结束时间、状态和可展示的结果摘要。
- **AuditEvent：**用户停用、设备变更、脚本发布和授权变更等关键管理操作。

服务端每次签发脚本清单或下载地址时都校验用户、设备和脚本授权，不依赖客户端隐藏界面来实现权限控制。运行日志采用必要信息最小化原则，不上传脚本运行中读取到的原始屏幕内容或敏感数据，除非产品后续明确设计并取得用户同意。

## 7. API 范围

MVP 可先提供以下 REST API：

- `POST /auth/login`、`POST /auth/refresh`：登录和续期。
- `GET /me`：获取当前用户和账号状态。
- `POST /devices`、`GET /devices`、`DELETE /devices/{id}`：设备绑定、查询和解绑。
- `POST /scripts`、`GET /scripts`：创建脚本元数据和查询可访问脚本。
- `POST /scripts/{id}/versions`、`GET /scripts/{id}/versions`：上传及查询版本。
- `POST /devices/{id}/sync`：获取当前设备可用的任务清单。
- `GET/POST /tasks/{id}/publications`、`DELETE /tasks/{id}/publications/{publication_id}`：管理员向指定设备分发版本、查看和撤销分发。
- `POST /devices/{id}/publications/{publication_id}/accept`：设备用户确认接收脚本版本。
- `POST /remote-runs`：为已授权脚本和目标设备创建远程运行请求。
- `GET /devices/{id}/remote-runs`：设备轮询待处理请求。
- `PATCH /remote-runs/{id}`：设备端客户端在服务端校验后自动批准请求，或上报执行状态。
- 遗留有限预授权 API 为旧客户端兼容保留，不参与当前 Android 客户端的远程执行判断。
- `POST /runs`、`PATCH /runs/{id}`：上报运行开始、结束状态和结果摘要。
- 管理接口：用户停用、设备管理、版本发布与运行记录查询。

脚本包使用短时有效的对象存储上传/下载地址，避免通过 API 服务进程中转大文件。所有管理接口均需做角色和资源归属校验。

## 8. MVP 范围与验收

### 首版实现

- 一个管理员角色和一个普通用户角色。
- 用户登录、设备绑定及多设备查看。
- 用户上传 Python 脚本、查看脚本版本和更新说明。
- 一种目标自动化场景及一组最小原生桥接能力。
- 用户在手机端运行脚本，或从后台发起远程运行请求；远程请求在服务端校验通过后自动运行，任务可见并可停止。
- 远程 OCR/屏幕捕获仍需设备用户授予 Android 系统授权；服务端脚本授权和 Android 系统权限均不能被客户端绕过。
- 运行期间显示状态、结果、日志摘要和停止入口。
- 管理员向用户/设备发布脚本，接收端确认后获取。
- 服务端权限校验、版本哈希校验、失败保留旧版本和基础审计记录。

### 首版暂不实现

- 任意 Python 包的完整兼容性保证、在线 IDE 和复杂依赖构建。
- 无限制的设备集群编排、无通知静默运行、不可停止的远程执行和复杂组织角色。
- 支付、套餐、自动续费和计费系统。
- 以“沙箱安全”为承诺的隔离执行环境。

验收重点是：用户能上传脚本、理解能力和权限范围、在设备上运行一个具体场景；也能从后台发起远程请求，在服务端校验通过后由设备自动启动，并查看运行状态和停止任务；运行成功或失败可在 App 和后台查看；无授权设备无法下载或运行脚本；更新校验失败不破坏当前可用版本。

## 9. 主要风险与前置验证

1. **动态执行与分发渠道政策：**当前首发渠道选为官网/私有服务器分发签名 APK，不提交 Google Play 审核。Android [官方动态代码加载指南](https://developer.android.com/privacy-and-security/risks/dynamic-code-loading)仍将远程动态加载代码视为高风险；脚本必须来自自有可信服务、使用 TLS 并在执行前校验哈希。私有分发需安全保管 APK 发布密钥，并对后续升级沿用同一密钥、递增 `versionCode`；安装用户须明确允许下载来源安装未知应用（见 [替代分发指南](https://developer.android.com/distribute/marketing-tools/alternative-distribution)）。若未来改为 Google Play 分发，必须重新核对其动态代码加载政策，必要时调整脚本执行/分发设计。
2. **Python Android 兼容性：**Chaquopy 支持的 Python 版本、ABI、依赖包和原生扩展需逐项验证。MVP 固定 Python 版本、ABI 和依赖白名单，不承诺所有 PyPI 包均可运行。
3. **脚本权限风险：**在 App 进程执行意味着脚本行为可能影响 App 可访问的数据和服务。运行确认能建立用户知情流程，但不能阻止恶意脚本；用户脚本与管理员推送脚本应有清晰来源标识和独立确认。
4. **无障碍与屏幕捕获：**能力设计必须围绕明确场景、用户知情和系统授权，不能承诺后台无提示地操作其他 App。
5. **任务可靠性：**Android 电量优化、进程回收和设备厂商差异会影响长任务。首版以已登录设备发起的短时、可见前台任务为准；不能保证离线设备收到请求或系统限制下自动启动。需要 Android 系统授权的远程任务仍须用户完成系统授权。

建议先做 Android 技术验证原型：选定目标 Android 版本和一个自动化场景，验证 Chaquopy 调用 Kotlin 桥接、权限授权、任务中止及目标渠道政策，再投入完整后台开发。
